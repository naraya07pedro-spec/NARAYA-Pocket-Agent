# ADR-0014 | Persisted observation sequence instead of clock/UUID ordering

Date: 10 November 2026
Status: MERGED via PR #19 as `772a075717b290ee990e5f99ec9e7adbd18ceb27`. Exact final PR HEAD `23923987a587ea6844d603ec0797eae7e384b360` passed 5/5 CI (65/65 backend/preflight, 11/11 local workerd/D1, 20/20 Android security JVM). No remote Cloudflare release, new owner authorization, paid resource or device test.

## Evidence-based problem

P1-L verified individual events and SHA continuity only when all `observed_at` values differed. On identical timestamps, mobile deliberately skipped predecessor checks because the Worker sorted observations using random event UUIDs as a tie-break. A wall clock can also move backward after an event is saved. Therefore neither timestamp nor UUID is a sound causal ordering key.

The existing `observations` table in 0001 is an ordinary SQLite rowid table. SQLite creates rowids automatically, normally increasing but **rowids are not a permanent guaranteed sequence** in all deletion and `VACUUM` scenarios. Storing a copy of current rowid during a controlled migration solves historical backfill without relying on ephemeral rowid values as a permanent API. SQLite's official [AUTOINCREMENT/ROWID specification](https://www.sqlite.org/autoinc.html) notes that automatic rowids can be reused after deletion. Cloudflare [D1 SQL compatibility](https://developers.cloudflare.com/d1/sql-api/sql-statements/) is SQLite-based. Neither document proves this query's performance on a real user's D1 Free quota.

## Decision

1. **Additive schema migration 0005**, after 0001–0004, adds `observations.event_sequence INTEGER`, copies each preexisting row's current SQLite `rowid` into the durable column, and creates a unique index plus `(monitor_id,event_sequence DESC)` lookup index. It does **not delete existing rows**, rewrite owner mapping, reset monitor versions, or alter preexisting scheduler quota/cursor values.
2. **Atomic future allocation**: the existing fenced scheduler `INSERT INTO observations ... SELECT ... FROM monitors` now includes `COALESCE((SELECT MAX(event_sequence) FROM observations),0)+1` in the **same SQL statement**. D1 SQLite serializes the write; the unique index fails closed if allocation collides. The existing D1 transactional `batch` retains observation insert, audit and monitor status update together. A successful ID allocation should be monotonically greater than all **currently retained** observations, but this is not a claim of never-reused IDs after administrative deletion of the maximum (which is why the API calls this a *retained insertion sequence*, not a globally immortal AUTOINCREMENT).
3. **Client-visible signed-user API** `GET /v1/sync/observations?monitorId=` returns `event_sequence` as a positive integer and sorts by `o.event_sequence DESC`, not `observed_at` or UUID. Exactly the same SQL owner/monitor filter and `LIMIT 50` remain. The old operator `/v1/observations` schema is intentionally not changed by this feature.
4. **Android fail-closed parsing**: `CloudSyncClient` requires an actual integer `event_sequence` from JSON (not a float, numeric string, null or guessed value), positive and strictly descending. The resulting order is used to test SHA adjacency of **every** consecutive CHANGE, regardless of equal timestamp or backward clock drift. At most one BASELINE may exist and it must be the oldest returned event; the oldest 50-event page may legitimately start after the original baseline. `observed_at` remains a positive timestamp for display and inspection, not evidence of causality.
5. **Avoid a half-migrated launch**: signed mobile `PATCH ACTIVE` checks the 0005 column in addition to the P1-J 0004 budget control. The scheduler itself checks it **before any provider GET or D1 quota reservation**, including when called with a legacy operator monitor. A stale pre-0005 Worker/Android contract must fail closed, not acknowledge a task it cannot write.
6. **Shared cross-runtime fixture v2** now has three explicit `event_sequence` values, and both Worker-owner HTTP and Android JVM parse the same JSON; the Node fixture is inserted oldest-first with actual SQLite sequence generation. Separate Node migration test seeds historical rows under 0001–0004, runs 0005, validates retained data and sequence even after local `VACUUM`, then inserts a new event with a **clock-regressed** timestamp and checks sequence order. Local Cloudflare workerd/D1 test proves three real local scheduler ticks with the **same fake millisecond** produce valid 1→2→3 order surviving local restart.
7. **Static preflight** requires migration 0005, new Worker ordering + allocation, and strict Android sequence checks; mutating the contracts fails CI. Remote readiness stays BLOCKED regardless of source PASS.

## Trade-offs and limitations

- Migrating a large remote D1 would write to **every existing observation** and create indexes. Cloudflare D1 Free quotas, backup/rollback plan, migration duration, actual CPU time and any account charges **have not been inspected**. **Never run this migration remotely without explicit owner approval, account-specific quotas and a verified backup**. Test on an owner-approved disposable environment first.
- `event_sequence` is a database insertion-order aid, not a cryptographic integrity proof, signed event log, independently verified GitHub response, chronological timestamp certificate, or evidence that Android was physically OFF. A compromised server or database administrator can rewrite both sequences and hashes.
- This design assumes the application remains the only writer and never performs independent per-event deletions out of order. SQLite `MAX+1` is monotonic among retained rows; deletion of newest rows could allow reuse across time. A future stronger externally auditable event ledger can use dedicated AUTOINCREMENT storage and an append-only hash chain, with different migration cost and evidence requirements.
- The app and backend must be upgraded together: Android now rejects observation results without `event_sequence`. The normal debug APK still has no Google Web Client ID or trusted Worker URL; there is no remote deployed backend or proven device installation.
- Reading a bounded latest-50 page verifies **internal** adjacency but not the omitted history or any true remote provenance. The per-monitor 3-row pilot quotas and global 3-attempt-per-UTC-quarter-hour budget are unchanged.
